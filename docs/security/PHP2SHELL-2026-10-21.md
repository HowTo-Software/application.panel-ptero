# PHP2Shell security update — 2026-10-21

## Scope and security impact

PHP released fixes for **CVE-2026-109618** and **CVE-2026-109619**, critical memory-safety vulnerabilities that can allow unauthenticated remote code execution under affected conditions. PHP **8.3.36** is the corrected release for the 8.3 branch. References: [PHP release archive](https://www.php.net/archive/2026.php), [CVE-2026-109618 advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [CVE-2026-109619 advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp).

The supplied production inspection reported PHP CLI and FPM **8.3.35**, Alpine 3.24.2, and the application image:

`ghcr.io/howto-software/howtoosoftware-panel-ptero@sha256:9e01bf0dcf38cca19beecafb94cb5316614c4fc35078d77f1aefad7ff1bf1914`

That production state was not independently inspected during this source-code update. There is no confirmed evidence of intrusion. **This commit, and even downloading a patched PHP base image, do not replace the running production application.**

Local inventory under `HTS - SItes feitos` identified this repository as the PHP application with Composer and PHP Docker runtimes. The old `howtoosoftware-rework-main` directory contains three copied Pterodactyl PHP classes (`a.php`, `b.php`, `ptero/wsctl.php`), but no independent PHP image or deployment was identified. The inspected creation-site, Linkatura and Web.Hosting projects had no application PHP files. This is not proof that other HTS servers or external repositories are patched: inventory their actual PHP CLI/FPM runtimes separately. A .NET or Node application does not receive a PHP runtime update from this patch.

## Files and compatibility

- `Dockerfile`: pin the patched FPM base and check the actual interpreter during the build.
- `.github/ci/Dockerfile`: pin patched PHP CLI while preserving the existing CI dependencies.
- `.github/ci/assert-php-version.php`: require actual PHP 8.3.36 or a later 8.3 patch; do not trust Composer's simulated platform or image labels.
- `.github/ci/verify-runtime.sh`: compare CLI/FPM versions; check extensions, Composer platform requirements, FPM/Nginx/Supervisor configuration, application assets, absence of baked environment files, PHP syntax and an isolated Laravel kernel boot.
- `.github/workflows/checks.yaml`: refresh and validate the toolchain, guard PHP jobs and build/check the final image without deployment.
- `.github/workflows/deploy.yaml`: pull pinned bases, validate the published image before exporting its deployable digest, and guard manually selected images before calling the deployment script.
- `.github/docker/entrypoint.sh`: stop printing generated `APP_KEY` and `HASHIDS_SALT` values. Generation, reuse and persistence semantics are unchanged.
- `.dockerignore`: exclude nested `.env*` files, including a local `var/.env`, while retaining the root public `.env.example` build fixture.
- This advisory: verification scope and operator requirements.

No application/framework dependencies, lockfiles, migrations, authentication/Authentik flows, API/provisioning behavior, Nginx/FPM/Supervisor configurations, Compose project/volume names, or storage permissions are intentionally changed. Composer's `config.platform.php` remains a dependency-resolution baseline, not a runtime security assertion. The Node build stage ships only its built assets; Composer/extension-installer helper stages copy tools, not a second PHP interpreter. Existing broad storage permissions are a separate hardening topic, not changed in this emergency patch.

## Verification and boundaries

Local checks can validate Composer metadata, PHP syntax, shell syntax, source formatting, locked frontend dependencies, TypeScript, lint and production assets. The developer PC has PHP **8.3.33** and no Docker/WSL: the runtime guard correctly rejects that interpreter. It must not be weakened to make local checks green.

Completed locally: Composer metadata validation, PHP syntax validation (1,079 tracked files plus the new guard), formatting of the new guard, Bash syntax validation of both shell scripts and workflow shell steps, workflow YAML parsing, `yarn install --frozen-lockfile`, TypeScript and ESLint. The dependency install reports existing peer-dependency warnings; the lockfiles were not changed. The full local PHP-CS-Fixer dry run reports 877 files needing formatting, with CRLF-to-LF differences in this Windows checkout; it is not recorded as a pass and those unrelated files were not rewritten. Linux CI remains authoritative for the full formatting check.

The production frontend also compiled successfully with Webpack. On Windows, the exact `clean` script was run through Corepack/Git Bash and Webpack was then invoked with `NODE_ENV=production`, because the script's nested bare `yarn` executable is not installed globally. No package script was changed. Existing Tailwind line-clamp/asset-size notices remain unrelated to the PHP engine hotfix.

Actual Linux image construction, runtime/configuration checks, PHPStan and both PHPUnit suites must be verified in GitHub Actions. PHPUnit's shared bootstrap executes `migrate:fresh` and seeding: **never run it with a developer or production environment file**. CI uses its committed public `.env.ci` fixture and disposable MariaDB/MySQL service containers. Record the exact run and outcomes in the PR; queued, failed or unexecuted jobs are not passes.

The final-image checker overrides the normal entrypoint and uses `--network none`, no production environment file and no persistent volumes. Its ephemeral test key is never printed or persisted. `artisan --version` checks kernel boot, not a complete HTTP/SSO/queue regression. Compose validation disables automatic `.env` loading, interpolation and service `env_file` resolution; it does not start a stack.

Example isolated commands (CI only, not a production deployment):

```sh
docker build --pull --no-cache --tag hts-panel-php-check:review .
docker run --rm --network none --entrypoint /bin/sh hts-panel-php-check:review /app/.github/ci/verify-runtime.sh
COMPOSE_DISABLE_ENV_FILE=1 docker compose -f deploy/compose.prod.yml config --no-env-resolution --no-interpolate --quiet
```

Track these milestones separately: **source corrected → complete image built and validated → final application image published → production container replaced and verified**. PR image checks do not publish the production application image and do not replace production. The toolchain job may publish a separate CI-only image.

## Deployment blockers and operator checklist

1. Review and approve the PR only after all required checks pass. No merge, workflow dispatch, SSH or production deployment was performed as part of this source update. A merge/push to `master` triggers the existing release workflow.
2. **Approval protection is not currently guaranteed:** read-only GitHub API checks on 2026-10-21 returned `protection_rules: []` for the `production` environment and `protected: false` for `master`. The environment name alone is not an approval gate. An authorized administrator must configure required reviewers and appropriate branch protection before any release merge; this patch does not change GitHub settings.
3. Take a verified database backup, preserve encrypted configuration and persistent volumes, and validate the restore procedure in an isolated environment. Keep sensitive backups outside the repository and CI logs.
4. Preserve Compose project `howtoosoftware-panel`, volumes `howtoo_var` and `howtoo_logs`, and the existing Authentik local-resolution mapping. Never run `docker compose down -v`, delete/rename volumes, rotate `APP_KEY`/`HASHIDS_SALT`, or run destructive Docker cleanup for this update.
5. Compare the intended release against the **actually deployed revision**, not just this patch. This patch adds no migrations, but intervening application commits may have pending migrations or seed changes. Review them before approving the release.
6. The unchanged production entrypoint executes `php artisan migrate --seed --force` on **every startup**, including an attempted rollback. Approve its database impact explicitly. Do not run that entrypoint for standalone version checks. Neither CI image checks nor this patch run production migrations.
7. Retain the previous application digest above and record the validated new **HTS GHCR image digest**, matching source revision, successful CI run and CLI/FPM outputs. An upstream `php:*` digest cannot replace the full application image in Compose.
8. Understand rollback limitations: `deploy/deploy.sh` reverts the application image, **not the database**. Its automatic fallback can restore the vulnerable 8.3.35 image and can execute startup migrations/seeding again. The new manual-workflow version guard rejects that old image for a normal manual deployment, but does not rewrite the existing automatic fallback behavior. Agree an incident-specific recovery plan; do not treat availability rollback as a completed security remediation.
9. Perform an explicitly approved release through the established pipeline. Afterwards independently check the running container's application digest/revision, `php -v`, `php-fpm -v`, health/login, API authorization, assets, Authentik SSO, queue workers and scheduled jobs. Confirm existing encrypted data remains readable without changing its key.
10. Review prior runtime/build/access logs for possible secret exposure or compromise indicators through a restricted channel; do not paste secrets or user data into issues/PRs. Old logs may contain keys from the former entrypoint. Removing future logging does not erase old logs or prove that keys were never exposed. Any rotation requires a separate planned encrypted-data migration, not an automatic hotfix step.

Until the final running-container checks succeed, the production PHP2Shell risk remains outstanding.
